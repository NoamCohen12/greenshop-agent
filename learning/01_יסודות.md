## 1.1 LangChain מול LangGraph

### LangChain
ספרייה שנותנת עטיפה אחידה לעבודה מול מודלי שפה. במקום ללמוד את ה-API של OpenAI, ואז של Ollama, ואז של Anthropic — כותבים קוד אחד שעובד מול כולם.

בפרויקט שלנו זה בא לידי ביטוי בדיוק בזה: הקובץ `model_provider.py` מחזיר או `ChatOpenAI` או `ChatOllama`, ושאר הקוד לא יודע ולא מעניין אותו באיזה מהם מדובר. לשניהם יש אותה מתודה `invoke()` שמחזירה אותו סוג אובייקט.

LangChain גם נותנת מושגים נוספים: כלים (Tools), זיכרון שיחה, ותבניות פרומפט.

### LangGraph
ספרייה **נפרדת** (מאותם מפתחים) שמטרתה שונה: לבנות **זרימות עבודה מורכבות** של סוכנים.

ההבדל המהותי:

| | LangChain | LangGraph |
|---|---|---|
| מה בונים | שרשרת ליניארית: A → B → C | גרף עם הסתעפויות ולולאות |
| החלטות | קבועות מראש בקוד | דינמיות, בזמן ריצה |
| מתאים ל | משימה פשוטה | מערכת עם מסלולים שונים |

**אנלוגיה:** LangChain זה כמו מתכון — שלב אחרי שלב, תמיד באותו סדר. LangGraph זה כמו מפת ניווט — יש צמתים, ובכל צומת מחליטים לאן ממשיכים לפי המצב.

**למה הפרויקט שלנו חייב LangGraph:** הדרישה במסמך היא ש"הפרויקט יהיה מנוהל ע"י גרף חכם שמקבל החלטות". שאלה על מדיניות הולכת למסלול אחד, שאלה על הזמנה למסלול אחר. זה לא רצף קבוע — זו החלטה.

## 1.2 State — לב העניין

ה-State הוא **מבנה נתונים שעובר בין כל הצמתים ומצטבר תוך כדי**.

תחשוב על טופס שעובר בין פקידים במשרד. הפקיד הראשון ממלא שדה אחד, מעביר הלאה. השני קורא מה שכתוב, ממלא שדה נוסף, מעביר. בסוף הטופס מלא.

בפרויקט שלנו ה-State מוגדר כך (בקיצור):

```python
class GreenShopState(TypedDict):
    user_message: str              # מה הלקוח שאל
    is_input_valid: bool           # צומת 1 ממלא
    route: str                     # צומת 1 ממלא
    retrieved_context: str         # צומת 2 ממלא
    tool_result: str               # צומת 3 ממלא
    draft_answer: str              # צומת 4 ממלא
    final_answer: str              # צומת 5 ממלא
```

**נקודה חשובה:** כל צומת מחזיר **רק את השדות שהוא שינה**, לא את כל ה-State. LangGraph ממזג את זה אוטומטית.

למשל, צומת ה-Retrieval מחזיר:
```python
return {"retrieved_context": context_text}
```
ולא נוגע בשאר השדות — הם נשארים כמו שהיו.

### למה TypedDict?

`TypedDict` זה מילון רגיל של Python, אבל עם הצהרה על אילו מפתחות אמורים להיות בו ומאיזה טיפוס.

```python
# מילון רגיל - אין הגנה
state = {"user_mesage": "שלום"}   # שגיאת כתיב! לא ייתפס

# TypedDict - העורך יסמן שגיאה
state: GreenShopState = {"user_mesage": "שלום"}   # מסומן באדום
```

זו בדיקה **סטטית** — היא עוזרת בזמן כתיבת הקוד, לא בזמן ריצה. בזמן ריצה זה פשוט מילון.

**שאלה אפשרית במבחן:** "למה לא השתמשת ב-class רגיל?"
**תשובה:** LangGraph מצפה למבנה מילוני כדי שיוכל למזג עדכונים חלקיים מכל צומת. TypedDict נותן את בטיחות הטיפוסים בלי לוותר על זה.

## 1.3 Node — צומת

צומת הוא פשוט **פונקציית Python** שמקבלת State ומחזירה עדכון.

```python
def retrieval_node(state: GreenShopState) -> dict:
    vector_store = get_vector_store()
    results = vector_store.similarity_search(state["user_message"], k=3)
    context = "\n\n".join(doc.page_content for doc in results)
    return {"retrieved_context": context}
```

זה הכל. אין קסם — פונקציה רגילה. מה שהופך אותה לצומת זה שרשמנו אותה בגרף:

```python
graph.add_node("retrieval", retrieval_node)
```

## 1.4 Edge — קשת

הקשת אומרת לגרף **לאן ממשיכים אחרי צומת**.

### קשת רגילה
```python
graph.add_edge("retrieval", "generation")
```
"אחרי Retrieval, תמיד לך ל-Generation." בלי תנאים.

### קשת מותנית (Conditional Edge)
כאן נמצאת האינטליגנציה. שני חלקים:

**חלק א' — פונקציית החלטה** שמסתכלת ב-State ומחזירה מחרוזת:

```python
def route_after_input_guardrail(state) -> str:
    if not state["is_input_valid"]:
        return "blocked"
    if state["route"] == "customer_specific":
        return "customer_specific"
    return "knowledge_question"
```

**חלק ב' — מפת יעדים** שמתרגמת כל מחרוזת לצומת:

```python
graph.add_conditional_edges(
    "input_guardrail_router",       # אחרי איזה צומת
    route_after_input_guardrail,    # מי מחליט
    {
        "blocked": "blocked_input",           # מחרוזת → צומת יעד
        "knowledge_question": "retrieval",
        "customer_specific": "tool_execution",
    },
)
```

**שים לב:** פונקציית ההחלטה **אינה צומת**. היא לא מקבלת מקום בגרף ולא משנה את ה-State. היא רק קוראת ומצביעה.

בפרויקט שלנו יש **שתי** קשתות מותנות:
1. אחרי Input Guardrail — לאיזה מסלול ללכת
2. אחרי Output Guardrail — לסיים או לנסח מחדש

## 1.5 אוטונומיה — מה זה אומר

המסמך דורש ש"המערכת לא יכולה להיות שרשרת ליניארית קבועה. הסוכן חייב להיות מסוגל לקבל החלטה איזה Tool להפעיל בעצמו."

### מה זה **לא** אוטונומיה

```python
# רצף קבוע - הקוד מחליט הכל
order_id = extract_number_with_regex(message)
result = call_n8n("order_status", order_id)
```

כאן המתכנת החליט מראש. אם הלקוח כותב "ההזמנה שהזמנתי בשבוע שעבר, 12345, לא הגיעה" — regex ימצא אולי גם "שעבר" או ייכשל.

### מה כן

```python
agent = create_agent(model=model, tools=[call_n8n_webhook], system_prompt=...)
response = agent.invoke({"messages": [HumanMessage(content=state["user_message"])]})
```

כאן **המודל** קורא את ההודעה, מבין שמדובר בבירור משלוח, מזהה ש-12345 הוא מספר ההזמנה, ומחליט לקרוא לכלי עם הפרמטרים הנכונים.

### תבנית ReAct

השם מגיע מ-**Reasoning + Acting** — לולאה של:

1. **חשיבה** — "הלקוח שואל על הזמנה. אני צריך לבדוק במערכת."
2. **פעולה** — קריאה לכלי
3. **תצפית** — קבלת התוצאה
4. **חזרה ל-1** — "יש לי את המידע. אפשר לענות."

זה ההבדל בין מודל שפה לסוכן: **מודל שפה מייצר טקסט. סוכן מבצע פעולות בעולם.**

## סיכום — מפת המושגים

```
StateGraph  ← המבנה הכולל
   │
   ├── State        ← הנתונים שעוברים (TypedDict)
   ├── Node         ← פונקציה שמעבדת State
   ├── Edge         ← מעבר קבוע בין צמתים
   └── Conditional  ← מעבר לפי החלטה בזמן ריצה
       Edge
```
