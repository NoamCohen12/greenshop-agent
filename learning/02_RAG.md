## 2.1 הבעיה ש-RAG פותר

מודל שפה יודע רק מה שהיה בנתוני האימון שלו. הוא לא מכיר את מדיניות ההחזרות של GreenShop, לא את קטלוג המוצרים, ולא את המחירים.

יש שלוש דרכים לתת לו את המידע:

| גישה | מה זה | חיסרון |
|---|---|---|
| **Fine-tuning** | לאמן מחדש את המודל על הנתונים שלך | יקר, איטי, וכל עדכון מדיניות דורש אימון מחדש |
| **הכל בפרומפט** | לדחוף את כל המסמכים לכל שאלה | חלון ההקשר מוגבל, עלות גבוהה, המודל "מתבלבל" בהרבה טקסט |
| **RAG** | לשלוף רק את הקטעים הרלוונטיים ולצרף אותם | — |

**RAG** = Retrieval-Augmented Generation — "יצירה מועשרת בשליפה".

הרעיון: במקום לתת למודל את כל המידע, נותנים לו רק את מה שרלוונטי לשאלה הנוכחית.

**שאלה אפשרית במבחן:** "למה לא עשית fine-tuning?"
**תשובה:** מדיניות החברה משתנה. ב-RAG מעדכנים קובץ טקסט ומריצים מחדש את ה-ingestion — דקות. ב-fine-tuning זה אימון מחדש של המודל. בנוסף, RAG מאפשר לצטט מקורות ומקטין הזיות, כי המודל מתבסס על טקסט שהוצג לו ולא על "זיכרון" מעורפל.

## 2.2 Embedding — משמעות כמספרים

**embedding** הוא וקטור — רשימת מספרים — שמייצג את המשמעות של טקסט.

```
"מדיניות החזרות"  →  [0.23, -0.81, 0.45, ... ]   (1536 מספרים)
"תנאי החזרת מוצר"  →  [0.25, -0.79, 0.43, ... ]   (דומה מאוד!)
"מתכון לעוגה"      →  [-0.67, 0.12, 0.88, ... ]   (רחוק)
```

**התכונה המרכזית:** טקסטים בעלי משמעות דומה מקבלים וקטורים קרובים במרחב, **גם אם אין להם מילים משותפות**.

זה ההבדל מחיפוש מילים רגיל:
- חיפוש מילולי: "החזרת מוצר" לא ימצא מסמך שכתוב בו "זיכוי כספי"
- חיפוש סמנטי: ימצא, כי המשמעות קרובה

### איך מודדים קרבה

הדמיון נמדד בדרך כלל ב-**cosine similarity** — הזווית בין שני הוקטורים. ככל שהזווית קטנה יותר, המשמעות דומה יותר.

### בפרויקט שלנו

```python
def get_embedding_model():
    provider = os.environ.get("MODEL_PROVIDER", "ollama").lower()
    if provider == "ollama":
        return OllamaEmbeddings(model="nomic-embed-text")
    return OpenAIEmbeddings(model="text-embedding-3-small")
```

**נקודה קריטית להבנה:** מודל embedding הוא **לא** מודל השיחה. הם שני מודלים שונים לגמרי:
- מודל שיחה (`gpt-4o-mini`) — מקבל טקסט, מייצר טקסט
- מודל embedding (`text-embedding-3-small`) — מקבל טקסט, מייצר וקטור

**ולכן:** מודלי embedding שונים מייצרים וקטורים במימדים שונים ובמרחבים שונים. אם בנית את המסד עם מודל אחד ומחפשת עם אחר — התוצאות יהיו אקראיות. זו הסיבה שהחלפת `MODEL_PROVIDER` מחייבת בנייה מחדש של `chroma_db`.

## 2.3 Chunking — פיצול המסמכים

לא מכניסים מסמך שלם למסד. מפצלים אותו לקטעים (chunks).

### למה?

1. **דיוק** — אם המסמך כולו וקטור אחד, הוא מייצג "ממוצע" של כל הנושאים שבו. קטע קצר ממוקד יותר.
2. **חלון הקשר** — אי אפשר לדחוף מסמך של 50 עמודים לפרומפט.
3. **רלוונטיות** — שאלה על משלוחים לא צריכה להביא גם את כל מדיניות ההחזרות.

### בפרויקט שלנו

```python
splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50,
    separators=["\n\n", "\n", ". ", " ", ""],
)
```

**מה עושה `Recursive`:** מנסה לפצל לפי הסדר ברשימה. קודם בגבולות פסקה (`\n\n`). אם קטע עדיין ארוך מ-500 — מנסה שורה (`\n`). אחר כך משפט (`. `). רק כמוצא אחרון — באמצע מילה.

**למה 500?** מספיק גדול לכלול רעיון שלם (סעיף מדיניות), מספיק קטן להישאר ממוקד.

**למה `overlap=50`?** כדי לא לאבד הקשר בגבול. דוגמה:

```
ללא חפיפה:
  chunk 1: "...זיכוי כספי מלא יינתן עבור מוצרים שהוחזרו תוך 14 יום."
  chunk 2: "בין היום ה-15 ל-30, ניתן לקבל זיכוי בשובר קנייה בלבד."
```

אם שואלים "מה קורה אחרי 14 יום?" — chunk 2 לבד חסר את ההקשר של "זיכוי כספי". החפיפה מבטיחה שסוף chunk 1 מופיע גם בתחילת chunk 2.

## 2.4 Vector Database

מסד נתונים שמאחסן וקטורים ויודע למצוא את הקרובים ביותר לוקטור נתון — במהירות.

חיפוש נאיבי היה משווה את שאילתת החיפוש לכל וקטור במסד. Vector DB משתמש באינדקסים מיוחדים (כמו HNSW) שמאפשרים חיפוש מהיר גם במיליוני וקטורים.

### למה ChromaDB

| שיקול | ChromaDB | Pinecone | FAISS |
|---|---|---|---|
| מקומי | ✓ | ✗ (שירות ענן) | ✓ |
| שמירה לדיסק | ✓ מובנה | ✓ | דורש עבודה ידנית |
| קל ב-Docker | ✓ | דורש מפתח API | ✓ |

בחרנו ChromaDB כי הוא מקומי (אין תלות בשירות חיצוני או במפתח נוסף), שומר לדיסק אוטומטית, ונארז בקלות ב-Docker.

### התהליך המלא

**שלב א' — Ingestion (חד-פעמי):**
```
קבצי טקסט → פיצול ל-chunks → embedding לכל chunk → שמירה ב-ChromaDB
```

**שלב ב' — שליפה (בכל שאלה):**
```
שאלת הלקוח → embedding → חיפוש 3 הקרובים ביותר → צירוף לפרומפט
```

```python
results = vector_store.similarity_search(state["user_message"], k=3)
```

`k=3` — מספר הקטעים שנשלפים. יותר מדי מכניס רעש, מעט מדי עלול לפספס.

## 2.5 מטא-דאטה

כל chunk נשמר עם מידע נוסף עליו:

```python
Document(
    page_content=file.read(),
    metadata={"source": os.path.basename(file_path)},
)
```

**למה זה חשוב:**

1. **ציון מקורות** — אפשר לומר ללקוח "לפי מדיניות ההחזרות שלנו..." ולדעת מאיפה הגיע המידע.
2. **סינון** — אפשר לחפש רק בקובץ מסוים:
   ```python
   vector_store.similarity_search(query, k=3, filter={"source": "return_policy.txt"})
   ```

המסמך דורש במפורש: "מומלץ לא להסתפק בשליפה סמנטית פשוטה, אלא להראות שימוש בסינון מבוסס מטא-דאטה או שיטות כמו Multi-Query."

**מה זה Multi-Query:** במקום לחפש עם השאלה המקורית בלבד, מייצרים ממנה כמה ניסוחים שונים ומחפשים עם כולם. מגדיל סיכוי למצוא את הקטע הנכון גם אם הלקוח ניסח בצורה לא צפויה.
